What happens today

The loop is closed. The first pass of this review found two breaks: the engine discarded the editor's unsaved text on intake, and it published nothing back. Both are fixed. Contract v2 keeps the editor's fields (and preserves ones it does not recognise), a content-view index decides which bytes count as current for each path, and the engine writes findings.jsonl and engine.json atomically for one side pane to render. The adapter and the engine now hash a buffer to the same value, which is what every freshness claim downstream rests on.
Still open: outbox.jsonl has no writer, because the engine has no language-server question to ask yet; the inbox tail has no durable watermark, so a mid-session engine restart is not yet trustworthy; and action/dismiss are accepted but not acted on.
  1. Start observation. Run uv run companion --root /path/to/project watch. In Neovim, configure the adapter and run :CompanionStart. Engine autostart is optional. Filesystem observation works independently of Neovim and defaults to .py files.
  2. Observe and snapshot. Filesystem changes and the editor inbox enter the engine queue. Cursor events are only logged; diagnostics are stored for republication; goal, dismiss, LSP-result and session-end are routed as session events with no file analysis. Content events resolve their bytes from the editor's canonical text (whose declared hash is recomputed, never trusted), then a recorded SHA, then disk. Each state is stored with an origin: editor content exists only in a buffer, disk and git content is what shelling-out tools can see. First live observation tries Git HEAD as a baseline; bytes and history are stored under .companion/snapshots/, the dirty-buffer overlay under view.json.
  3. Schedule useful changes. The same bytes in the same place end processing. The same bytes moving from buffer to disk still schedule work, because tools that read the working tree can finally see them. Changed bytes submit a path bundle, mark dependent evidence stale, requeue defining files, and additionally requeue any claim whose callee this file now names but never depended on — a newly written caller that staleness alone cannot catch. The single worker debounces for 400 ms and replaces older pending bundles for the same path.
  4. Interpret structure. Python tree-sitter compares a baseline to the current content. The baseline depends on origin: an unsaved buffer is compared against the last saved content, so an edit typed across several debounce windows reads as one change rather than a stream of drafts; a save is compared against the previous save. It identifies changed signatures, removed functions, new functions, parse errors or no useful structural change. Git HEAD seeds history.
  5. Investigate. For changed or removed signatures, search candidate files with rg and every unsaved buffer naming the callee — rg reads files, so a call typed a second ago is invisible to it — then read each candidate at its effective revision and judge call arguments with tree-sitter. Verdicts are breaks, unsure or ok. If configured and breaking sites exist, request one model sentence. After task processing, run pytest on test files mentioning affected names, unless --no-tests is set or the content is buffer-only: pytest imports the working tree and cannot see a buffer, so its evidence is labelled saved-revision-only and names the buffers it could not speak for.
  6. Preserve and present evidence. Records carry dependency SHAs and a fingerprint that includes the revision label, so a claim moving from buffer to saved file counts as an update rather than an unchanged record. Identical fresh claims are not re-appended. A completed bundle rewrites the board and quickfix file, and publishes findings.jsonl and engine.json whole and atomically. The developer opens the pane voluntarily; it hands the cursor straight back, and the engine never opens a window or applies a patch.
WatchFilesystem + inbox producers; scheduler worker runs in a background thread.
IngestExplicit file paths; handles events and drains pending bundles immediately.
ReplayCopies recorded objects and processes events without reading the target working tree. Tests produce skipped records; an explicitly configured model can still be called.

Replay reproduces snapshot-based analysis, not live test execution or model determinism. CLI usage and behavior above come from cli.py and engine.py.

What is still open

The order below is a proposed discussion order, not a newly agreed roadmap. “Code” means verified by inspection; historical measurements remain attributed to the handoff.

PriorityGap / decisionCurrent evidence and completion criterion
1 · Trust the stateRestart watermarkCode: the inbox tail still starts at byte zero and the engine deduplicates only by content SHA, so a mid-session restart re-reads the whole inbox. Complete when an accepted-event watermark per session survives a restart and a restart integration check proves no work is repeated or lost. This is the largest remaining correctness item.
1 · Trust the stateStorage retentionCode: full buffer text accumulates in inbox.jsonl (the engine no longer copies it into its own log, but the adapter’s append-only inbox is unbounded) and snapshots have no garbage collection. findings.jsonl, engine.json and view.json are written atomically; state.json and board.md still are not. Decide retention, then make the remaining writes atomic too.
2 · Act, do not only reportActions and dismissalCode: every published finding carries action: null, and dismiss events are logged and ignored. These are the two places the system accepts input it does not act on. Complete when an action round-trips through outbox.jsonl with a freshness re-check before applying, and a dismissal is a suppression record keyed to the evidence so it expires when the evidence changes.
2 · ConcurrencyTwo editors, and writers that are not the editorCode: the engine follows one session; a new session id clears the previous one’s overlays, which is right for handoff between editors and wrong for two at once. A file written by something else while a buffer is dirty keeps its overlay by design, but there is no explicit conflict state. Ingestion and the worker still share mutable stores without an evidence-store lock. Decide the ownership model, then exercise simultaneous producers.
3 · Broaden factsLanguage-server integrationCode: detection and caller judgment are Python-specific. The adapter answers LSP requests, but the engine never asks, so outbox.jsonl has no writer. Adapter result conversion assumes lists of locations, insufficient for hover/document-symbol results; request timeout and error behavior also need work. Complete an end-to-end LSP path before claiming Rust/JS support.
3 · Background testsPolicy and isolated executionCode: tests are enabled by default, selected by name occurrence, and run in the target working tree using the companion interpreter or available pytest. The saved-revision limit is now stated in the evidence and in the published finding, rather than left implicit — but no frozen sandbox or project policy tiers exist, and unsaved code is simply not tested. Decide per-project off / draft / run / incorporate rules, interpreter selection, and whether a materialized overlay runner is worth it. Test generation is still absent.
4 · Optional interpretationModel profiles and suggestion qualityCode: the CLI still takes a raw --model; the agreed profile abstraction (local-qwen3-coder, local-fast, flagship) is designed and unbuilt. The model payload includes the first 12 sites regardless of verdict, and empty or unsuitable output is not validated. engine.json already carries a model block and the pane renders it, so wiring is additive. Handoff: breaking-only payloads were more stable on the measured desktop.
4 · ContextQMD warmup and provenanceCode: engine.json reports context: qmd disabled and the pane renders it; nothing else exists. Retrieval returned both proposal and historical documents in the smoke test, so provenance per passage is a requirement, not a refinement. Complete when warmup is asynchronous, visible as warming/ready/unavailable, and every passage carries source path, revision, document status and query provenance.
5 · Product breadthLater capabilitiesCode + vision: the pane renders Callers and Errors; Docs and Roadmap are buckets with no producer. Docs retrieval, Chat, Roadmap observer, test generation and runtime Compare are not implemented. Named freeze read/write helpers exist, but no user-facing Freeze/Compare workflow.
MaintenanceDocs and verificationDone this pass: the README no longer references absent commands; the contract is v2 and matches the code; canonical text has its own specification and cross-language fixtures. The check harness grew from 18 checks with two confirmed gaps to 36 checks with none, and the unit suite from 5 tests to 60. The plugin smoke script still injects fake findings, which is now its stated purpose — the harness covers real engine→editor integration.

Decisions to discuss after the integration gaps

  • Next milestone: the unsaved-edit loop is done and verified. Is the restart watermark the right next item, or should model profiles come first because they are what the developer would actually notice?
  • Project policy: test execution defaults, when incorporation is allowed, and which projects may send code to remote models.
  • Docs and Roadmap: version-specific documentation sources, offline cache behavior, and how suggestions expire without becoming developer decisions.
  • Deployment constraints: laptop measurements, retention limits, and whether JSONL remains sufficient. Python and a future socket/MCP transport remain design choices, not prerequisites for completing the current loop.
The previous milestone, and where it stopped. “Make an unsaved Python signature edit appear as a current, evidenced caller finding in Neovim; fix the caller and watch that finding clear; restart either side without replaying old work.” The first two thirds are done and asserted in the harness, including fixing the caller in a buffer that was never saved. The last third — restarting either side without replaying old work — is the watermark item at the top of the table, and is the one thing left from this scenario.
